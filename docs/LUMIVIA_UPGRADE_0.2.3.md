# Lumivia 0.2.3 升级说明

本次同步官方 `v0.2.3`（`8fa67d477`），并纳入其后的唯一版本同步提交
`772a0382f079676983c06f24b0d41e09139a8462`，将 VERSION 更新为 0.2.3。
定制发布仍从 `goldenfishs/sub2api:main` 构建固定提交号镜像。

## 数据库与模型配置

- 保持已执行的 `235_subscription_auto_advance_week.sql` 原文件及校验和。
- 新增官方 `235_group_model_allowlist.sql` 与 `236_group_model_allowlist_repair.sql`。
  迁移器按完整文件名记账，两个不同文件名的 235 可以共存。
- 官方 235 将 `groups.models_list_config` 更名为 `model_allowlist`，保留 JSON 数据；
  236 处理缺列和双列并存等情况。此次迁移不修改订阅的额度、窗口、到期时间及自动开关。
- 模型配置的语义由仅过滤模型列表变为同时限制实际调用。部署前须检查已启用旧配置的分组。
  2026-09-08 本次生产只读预检中，启用的旧配置分组数为 0。

## 本次回退不能仅替换镜像

0.2.1 的旧应用查询 `groups.models_list_config`，而升级后通常只有 `model_allowlist`。
因此部署脚本保存的旧应用快照**不能单独保证本次回退可用**。部署时须有人检查失败后的状态，
不要把旧容器启动或 `/health` 响应当作涉及分组的接口已恢复。

如必须回退至旧 0.2.1 应用：

1. 停止 Sub2API 应用，保留当前数据库备份；PostgreSQL、Redis 和 Caddy 保持运行。
2. 检查 `groups` 列结构。仅当旧列不存在、新列存在，且未另做不兼容结构变更时，
   可以在事务中将 `model_allowlist` 改名回 `models_list_config`。这会保留列内数据。
   若两列并存或状态不同，先人工检查，不覆盖任何配置。
3. 启动本次部署保存的旧应用快照，验证密钥、订阅、分组查询及正常请求。
   不删除 `schema_migrations` 记录，不改迁移文件或校验和。

之后再次升级至 0.2.3 时，须停止应用并直接执行仓库原版
`backend/migrations/236_group_model_allowlist_repair.sql`，使结构恢复为新版预期，
再启动固定提交号的新镜像。236 的 SQL 可重复执行，但已记账的迁移不会在每次启动时重跑。

完整数据库备份恢复是另一种回退方式，但会覆盖备份后的写入，必须单独评估，不能自动执行。
上述列名回退步骤只适用于本次已审查的 0.2.1 ↔ 0.2.3 路径。

## 验证范围

- 手动/自动扣时、连续跳周和月周期推进、额度校验、更新来源、API 契约、行锁。
- 原首页、模型白名单、管理端订阅读取入口及中英文键完整性。
- 使用生产 schema 和合成数据在独立数据库演练迁移、旧列名回退与再次升级。
- 正式发布前等待 Fork 的 CI 与 Lumivia Release 检查通过；生产不使用真实订阅试扣时。
